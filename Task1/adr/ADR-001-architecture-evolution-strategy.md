# ADR-001. Стратегия эволюции архитектуры AdScale

## Статус

Accepted

## Дата

2026-06-18

## Контекст

AdScale работает как гибридный монолит на C++ / Go / Python / Node.js с единой PostgreSQL-инстанцией. Система уже находится близко к пределу:

- 15 000 RPS в пике;
- P95 latency 110-120 ms при требовании не более 100 ms;
- периодические деградации в часы пик;
- нет кэша, очередей, контейнеризации и автоматизированного деплоя;
- статистика, аналитика, финансы и RTB конкурируют за одну БД.

Подключение нового DSP-партнера увеличит нагрузку до 18 000 RPS в ближайшие 3 месяца. В течение года ожидается рост до 50 000 RPS и SLA 99,9%.

Полная остановка бизнеса невозможна. Полная перепись также невозможна из-за срока, бюджета и операционных рисков.

## Решение

Использовать Strangler Fig Pattern и постепенную декомпозицию монолита.

Первый этап:

- добавить DSP API Gateway перед новым внешним трафиком;
- выделить Bidding Service как latency-critical компонент;
- добавить Redis для hot data в RTB-пути;
- добавить Kafka для событий показов, кликов и win/loss events;
- изолировать аналитику от production-БД через отдельный read/analytics контур;
- контейнеризовать новые сервисы и добавить observability.

Дальнейшие этапы:

- выделить Campaign Service, Budget Service, Statistics Service, Analytics Service и Financial Service;
- перейти к Database per Service;
- оставить legacy monolith только для функций, которые еще не мигрированы;
- постепенно переводить внешний и внутренний трафик со старых функций на новые сервисы.

## Рассмотренные альтернативы

### Оставить монолит

Плюсы:

- минимальные изменения в краткосрочной перспективе;
- меньше новых технологий;
- ниже риск ошибок миграции данных.

Минусы:

- не решает проблему latency;
- не позволяет масштабировать Auction Engine и Statistics независимо;
- сохраняет PostgreSQL как single point of failure;
- события и аналитика продолжают конкурировать с RTB;
- высок риск штрафов и деградаций после подключения DSP.

Альтернатива отклонена, потому что не обеспечивает выполнение SLA при росте нагрузки.

### Полностью переписать систему на микросервисы сразу

Плюсы:

- можно сразу построить целевую архитектуру;
- лучшее разделение доменов и данных;
- потенциально высокая масштабируемость.

Минусы:

- невозможно надежно выполнить за 3 месяца;
- высок риск регрессий в RTB и финансовой логике;
- требуется больше SRE-практик, чем есть в команде сейчас;
- миграция данных и контрактов будет слишком большой;
- бизнес не получит быстрый защитный эффект для DSP-интеграции.

Альтернатива отклонена из-за срока, бюджета и риска остановки бизнеса.

### Модульный монолит

Плюсы:

- снижает сложность по сравнению с микросервисами;
- помогает упорядочить кодовые границы;
- может быть промежуточным шагом.

Минусы:

- не дает независимого горизонтального масштабирования критичных runtime-компонентов;
- не решает проблему общей БД без дополнительных изменений;
- хуже подходит для RTB hot path, где нужно изолировать latency и нагрузку.

Альтернатива может использоваться внутри legacy-кода, но не является достаточной целевой стратегией.

## Последствия

Положительные:

- быстрый фокус на самом критичном bottleneck: RTB-аукционе;
- снижение нагрузки на PostgreSQL за счет Redis и Kafka;
- возможность подключить DSP-партнера без полной переписи;
- постепенное накопление микросервисной и эксплуатационной зрелости;
- независимое масштабирование Gateway, Bidding и Event Sink.

Отрицательные:

- на время миграции появится гибридная архитектура: монолит плюс новые сервисы;
- потребуется управлять согласованностью данных между legacy и новыми сервисами;
- команда должна освоить эксплуатацию Kafka, Redis, контейнеров и observability;
- потребуется дисциплина контрактов API и событий.

## Критерии успешности

- Система выдерживает 18 000 RPS в течение 3 месяцев после начала работ.
- P95 latency RTB-пути не превышает 100 ms.
- События кликов и показов больше не пишутся напрямую в production-БД в синхронном критичном потоке.
- Аналитические запросы не влияют на latency аукциона.
- Gateway, Bidding Service и Event Sink масштабируются горизонтально.
- Есть метрики и алерты по RPS, latency, error rate, timeout rate, DB saturation и Kafka lag.
