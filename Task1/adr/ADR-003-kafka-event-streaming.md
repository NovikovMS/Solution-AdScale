# ADR-003. Выбор Apache Kafka как платформы для потоковой обработки событий

## Статус

Accepted

## Дата

2026-06-18

## Контекст

Statistics Service в монолите AdScale пишет события кликов и показов напрямую в PostgreSQL без буферизации. При текущей нагрузке 15 000 RPS это создаёт:

- высокую write-нагрузку на единственную PostgreSQL-инстанцию;
- конкуренцию write-операций с RTB-транзакциями и аналитическими запросами;
- риск потери событий при перегрузке БД;
- невозможность масштабировать ingestion независимо от остальной системы.

После подключения DSP-партнера нагрузка вырастет до 18 000 RPS, а через год ожидается 50 000 RPS. Каждый RTB-запрос генерирует как минимум одно событие показа, а каждый клик — дополнительное событие. Это означает объём событий, соизмеримый с RPS платформы.

Требования к решению:

- разгрузить RTB hot path от синхронной записи событий;
- гарантировать доставку событий без их потери;
- поддерживать несколько независимых потребителей: Statistics Service, Analytics Service, Financial Service;
- обеспечивать горизонтальное масштабирование ingestion;
- допускать воспроизведение (replay) событий для перестройки агрегатов или аналитических витрин.

## Решение

Использовать Apache Kafka как распределённую платформу потоковой обработки событий.

Топики и назначение:

| Топик | Назначение | Потребители |
|---|---|---|
| `ad.impressions` | Показы рекламы | Statistics Service, Analytics Service |
| `ad.clicks` | Клики по рекламе | Statistics Service, Analytics Service |
| `auction.win-loss` | Результаты аукциона | Statistics Service, Financial Service |
| `campaign.changed` | Изменения кампаний | Ad Server (cache invalidation), Bidding Service |
| `financial.events` | Финансовые операции | Financial Service |

Архитектурные решения:

- Delivery Service публикует события в Kafka асинхронно после формирования HTTP response, не задерживая ответ пользователю.
- Event Sink Service принимает события по HTTP от внутренних компонентов и публикует их в Kafka, изолируя монолит от прямой зависимости на брокер.
- Statistics Service и Analytics Service потребляют события из Kafka через отдельные consumer groups.
- Kafka сохраняет события с retention не менее 7 дней, что позволяет перестраивать агрегаты при сбоях.
- Схема событий фиксируется через Avro со Schema Registry для контроля совместимости между производителями и потребителями.

## Рассмотренные альтернативы

### Оставить прямую запись в PostgreSQL (текущее состояние)

Плюсы:

- нет новых технологий;
- прост в реализации и отладке.

Минусы:

- не масштабируется: write-нагрузка растёт пропорционально RPS;
- создаёт конкуренцию с RTB и финансовыми транзакциями;
- не поддерживает replay событий;
- PostgreSQL становится узким местом как для ingestion, так и для аналитики.

Альтернатива отклонена: не решает ни одну из ключевых проблем.

### RabbitMQ как брокер сообщений

Плюсы:

- проще в настройке, чем Kafka;
- подходит для task queues и RPC-паттернов.

Минусы:

- не предназначен для хранения и воспроизведения событий;
- при большом объёме событий производительность уступает Kafka;
- ограниченная поддержка множественных независимых потребителей с разными смещениями;
- нет нативного разбиения (partitioning) для горизонтального масштабирования по ключу.

Альтернатива отклонена: не подходит для event streaming с требованием replay и высокого throughput.

### Redis Streams

Плюсы:

- Redis уже используется в архитектуре;
- низкая latency;
- простая интеграция.

Минусы:

- ограниченное хранение событий по сравнению с Kafka;
- меньше возможностей для построения consumer group с гарантиями;
- не предназначен как основная платформа event streaming при объёмах порядка 50 000 RPS.

Альтернатива отклонена: Redis Streams используется как вспомогательный инструмент, но не как основная платформа ingestion.

### Облачные managed-решения (AWS Kinesis, GCP Pub/Sub)

Плюсы:

- не нужно управлять кластером;
- автоматическое масштабирование.

Минусы:

- привязка к конкретному облачному провайдеру;
- ограниченный контроль над настройками retention, партиционирования и консьюмер-групп;
- задание описывает on-premise или независимую инфраструктуру;
- дороже при больших объёмах данных.

Альтернатива не исключена для долгосрочной перспективы, но не является приоритетом на горизонте 3 месяцев.

## Последствия

Положительные:

- RTB hot path перестаёт быть заблокирован синхронной записью событий;
- Statistics Service и Analytics Service потребляют события независимо, без взаимного влияния;
- replay позволяет перестраивать агрегаты при изменении логики или сбое потребителя;
- горизонтальное масштабирование ingestion достигается добавлением партиций и консьюмеров;
- события не теряются при временной недоступности потребителей.

Отрицательные:

- команда должна освоить операционную модель Kafka: управление кластером, Schema Registry, consumer lag monitoring;
- увеличивается сложность инфраструктуры;
- необходима обработка дублирования событий (at-least-once delivery): потребители должны быть идемпотентны;
- Schema Registry добавляет зависимость, которую нужно поддерживать.

## Критерии успешности

- События кликов и показов больше не пишутся синхронно в PostgreSQL в критическом RTB-пути.
- Statistics Service и Analytics Service потребляют события через отдельные consumer groups без взаимного влияния.
- Kafka consumer lag для топиков `ad.impressions` и `ad.clicks` не превышает допустимого порога (не более 30 секунд задержки агрегации).
- Система выдерживает рост объёма событий при росте RPS без деградации RTB-пути.
- Replay событий за последние 7 дней работает корректно.
