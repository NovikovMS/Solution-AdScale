# Архитектурные драйверы

## Функциональные требования

| ID    | Требование | Приоритет |
|-------| --- | --- |
| FR-01 | Принимать bid requests от текущих и новых DSP-партнеров по OpenRTB | Must |
| FR-02 | Отвечать на bid requests в пределах SLA и возвращать корректный bid response | Must |
| FR-03 | Поддерживать управление кампаниями, ставками, таргетингом и бюджетами через рекламный кабинет | Must |
| FR-04 | Учитывать показы, клики и другие события без влияния на RTB hot path | Must |
| FR-05 | Выполнять финансовые операции: списания, пополнения, счета, балансы | Must |
| FR-06 | Предоставлять рекламодателям аналитику и отчетность | Should |
| FR-07 | Поддерживать подключение нескольких DSP-площадок | Should |
| FR-08 | Сохранять возможность постепенной миграции без остановки бизнеса | Must |

## Атрибуты качества

### 1. Производительность

Приоритет: Critical.ы

- Через 3 месяца система должна выдерживать не менее 18 000 RPS.
- Через год система должна масштабироваться до 50 000 RPS.
- P95 latency для RTB-пути не должен превышать 100 ms.
- Для нового DSP-партнера необходимо стремиться к стабильному ответу не более 80 ms.

Производительность является главным драйвером, потому что bid response после таймаута теряет бизнес-ценность: рекламодатель не участвует в аукционе, платформа теряет выручку и рискует штрафами.

### 2. Доступность и отказоустойчивость

Приоритет: Critical.

- Целевой SLA через год - 99,9%.
- Отказ одного экземпляра сервиса не должен останавливать RTB.
- Отказ аналитики или отчетности не должен влиять на обработку bid requests.
- База данных не должна оставаться единой точкой отказа.

### 3. Масштабируемость

Приоритет: Critical.

- Ad Server, Bidding Service и event ingestion должны масштабироваться горизонтально.
- Нагрузка на события должна масштабироваться независимо от финансов и кабинета.
- Аналитические чтения должны быть изолированы от транзакционной БД.

### 4. Эволюционность

Приоритет: High.

- Полная перепись системы невозможна.
- Архитектура должна позволять постепенное выделение сервисов из монолита.
- Старый и новый контуры должны работать параллельно в период миграции.

### 5. Наблюдаемость

Приоритет: High.

- Нужны метрики RPS, P50/P95/P99 latency, error rate, timeout rate, saturation.
- Нужны метрики Kafka lag, consumer errors, DB locks, cache hit ratio.
- Для критического пути нужны distributed traces.

### 6. Согласованность данных

Приоритет: High для финансов, Medium для статистики.

- Финансовые операции требуют строгой транзакционности и идемпотентности.
- События кликов и показов допускают eventual consistency, но не должны теряться.
- Аналитика может обновляться с небольшой задержкой.

### 7. Безопасность

Приоритет: Medium.

- Внешние DSP-интеграции должны проходить аутентификацию и rate limiting.
- Рекламный кабинет должен сохранять контроль доступа к кампаниям и финансовым данным.
- Внутренние сервисные вызовы должны быть защищены на уровне сети и сервисной идентичности.

## Ограничения

### Бизнес-ограничения

- Срок промежуточного решения - 3 месяца.
- Бюджет ограничен.
- Нельзя останавливать бизнес и отключать текущих клиентов.
- Нужно подключить крупного DSP-партнера без деградации SLA.
- Нет выделенных SRE, технического писателя и бизнес-аналитика.

### Технические ограничения

- Текущая система - гибридный монолит на C++ / Go / Python / Node.js.
- Сейчас используется одна PostgreSQL-инстанция.
- Кэш и очереди отсутствуют.
- Контейнеризация отсутствует.
- Деплой выполняется вручную.
- Архитектура не задокументирована.

### Организационные ограничения

- Команда 35 человек, поэтому решение должно быть реалистичным по сопровождению.
- Необходимо минимизировать количество новых технологий в первом этапе.
- Нужно выбирать технологии, для которых команда сможет быстро построить эксплуатационные практики.

## Ключевые архитектурные решения, вытекающие из драйверов

1. Использовать Strangler Fig Pattern вместо полной переписи.
2. Первым выделять Bidding Service, потому что он определяет выполнение SLA и выручку.
3. Разделить критичный RTB-путь и некритичные потоки статистики, аналитики и кабинета.
4. Добавить Redis для чтения campaign/bid/targeting данных в hot path.
5. Добавить Kafka для кликов, показов и downstream analytics.
6. Разделить базы данных по сервисным границам по мере декомпозиции.
7. Ввести API Gateway для DSP-интеграций, rate limiting, auth, circuit breaker и мониторинга.
