# Task1. Архитектурная диагностика и целевое видение AdScale

## Цель

Подготовить архитектурную диагностику текущей платформы AdScale и целевое видение эволюции системы на горизонт одного года.

Ключевой бизнес-драйвер: подключение крупной DSP-площадки без деградации SLA при росте нагрузки сначала до 18 000 RPS, затем до 50 000 RPS.

## Состав артефактов

- `AS-IS.md` - анализ текущей архитектуры, узкие места и риски.
- `drivers.md` - функциональные требования, атрибуты качества и ограничения.
- `TO-BE.md` - целевая архитектура и границы будущих сервисов.
- `diagrams/as-is.puml` - C4 Container диаграмма текущей архитектуры.
- `diagrams/to-be-container.puml` - C4 Container диаграмма целевой архитектуры (горизонт 1 год).
- `adr/ADR-001-architecture-evolution-strategy.md` - ADR: стратегия эволюции архитектуры (Strangler Fig).
- `adr/ADR-002-bidding-service-extraction.md` - ADR: выделение Bidding Service первым приоритетом.
- `adr/ADR-003-kafka-event-streaming.md` - ADR: выбор Kafka для потоковой обработки событий.

## Краткий вывод

Текущая архитектура является гибридным монолитом с единой PostgreSQL-инстанцией, отсутствием кэша, очередей, контейнеризации и автоматизированного деплоя. Основные риски сосредоточены в hot path RTB-аукциона, прямой записи событий в production-БД и конкуренции аналитических запросов с транзакционной нагрузкой.

Целевой подход - постепенная декомпозиция по Strangler Fig Pattern: сначала вынести наиболее критичные потоки ставок, событий и чтения кампаний, затем разделить данные по сервисам, добавить Kafka, Redis, API Gateway, observability и горизонтальное масштабирование.
